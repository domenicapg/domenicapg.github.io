Privacy Policy — Hermes Personal Backup

Effective date: 2026-11-23 · Last updated: 2026-11-23

Summary in one paragraph. Hermes Personal Backup is a private tool used by exactly one person. It makes an AES-256 encrypted archive of that person's own assistant data on that person's own computer and uploads that encrypted archive to a private folder in that same person's Google Drive. The data is never shared, never sold, never used for advertising, never read by another person, and never stored on any server operated for third parties. The only Google data the application can ever touch belongs to the single account that authorised it.

1. Who we are

“Hermes Personal Backup” is not a company. It is a piece of automation software written and operated by one private individual for their own use. The operator can be reached at aag262404@gmail.com. Because there is only one user — the operator themselves — there is no customer database, no analytics service, no advertising partner and no data-processing agreement with any third party.

2. What this application does

The application backs up the local data of a personal assistant program called Hermes (configuration files, scheduled-job definitions, conversation history and related state) so that the operator can restore their assistant after a hardware failure. It also optionally allows that assistant — never anyone else — to read or draft the operator's own Gmail messages, calendar events, contacts, documents, spreadsheets and tasks, so the assistant can carry out requests such as “summarise the mail that arrived today” or “put this on my calendar”.

3. Google data we access, and exactly why

Access is granted through Google OAuth 2.0 with explicit consent. The following scopes are requested. Each row states what is read or written and the specific purpose for which it is used.

Scope requestedWhat it permitsPurpose
drive Create, read, update and delete files in the Drive of the authorising account. To upload the encrypted backup archive into one specific private folder, list existing archives, and delete archives that have aged out of the retention schedule.
gmail.readonly Read mail and message metadata of the authorising account. To answer the operator's own requests about their own inbox (search, summarise, triage).
gmail.send Send mail as the authorising account. To send a message only when the operator has explicitly asked the assistant to send it, and only after the operator has seen and approved the content.
gmail.modify Change labels on the account's own messages (e.g. mark read, add a label). To apply triage actions the operator requested, such as marking a message read or labelling it.
calendar Read and modify events of the authorising account. To show and create the operator's own schedule entries when asked.
contacts.readonly Read the contacts of the authorising account. To resolve names to addresses for the operator's own requests (e.g. “mail my accountant”).
documents Read and edit the authorising account's Google Docs. To draft or edit documents the operator asked for.
spreadsheets Read and edit the authorising account's Google Sheets. To read or write spreadsheets the operator asked about.
tasks Read and modify Google Tasks of the authorising account. To maintain the operator's own to-do list when asked.

These are all of the scopes requested. No other data category — no precise location, no health data, no payment information, no browsing history, no photographs uploaded through Google Photos — is accessed. Access is limited to the content of the single Google account that granted consent; there is no domain-wide delegation and no service account acting on behalf of other users.

4. How the data is stored, encrypted and protected

  • Encryption before transfer. Each backup archive is compressed and encrypted with AES-256 (via OpenSSL) on the local machine, using a passphrase held only by the operator. The plaintext never leaves the machine and never reaches Google Drive in unencrypted form.
  • Where it rests. The encrypted archive rests in one private Google Drive folder of the authorising account. That folder is not shared with anyone and is not published on the web.
  • Local secrets. The OAuth refresh token and the client secret are stored in files on the operator's own machine, protected by filesystem permissions (mode 600, readable only by the service account that runs the backup).
  • No server-side copy. The application does not copy Google data to any external server, object store, logging service or third-party API. Messages and documents read for the operator are processed in memory for the duration of that request only.

5. How long data is kept (retention)

  • Backup archives in Drive: kept on a rolling schedule of 7 daily and 4 weekly copies. Older archives are deleted automatically, and each archive carries its own checksum files so integrity can be verified.
  • Credentials: the OAuth refresh token is retained only while it is needed to run the scheduled backup, and can be revoked at any time (see section 8).
  • Content read during an assistant request: not persisted. It is used to answer that request and then discarded from memory.

6. What we never do with the data

  • We do not sell, rent, licence or trade any Google user data.
  • We do not share it with any third party, for any reason, other than Google itself as the storage provider chosen by the operator.
  • We do not use it for advertising, marketing, profiling or automated decision-making.
  • We do not use Gmail content for advertising purposes in any form, including for training or improving any model used by anyone else.
  • We do not permit any human other than the operator to read it.
  • We do not transfer it to any model provider unless the operator has explicitly asked for a task that requires it, and even then only the minimum text necessary for that request.
  • We do not collect data about children. The tool is operated by one adult for their own data.

7. Google API Services User Data Policy

The application's use and transfer of information received from Google APIs adheres to the Google API Services User Data Policy, including the Limited Use requirements. In particular: we use the data only to provide or improve the user-facing features described on this page; we do not transfer it to others except as described here or as necessary to provide those features; and we do not use it for advertising, including targeted advertising.

8. Your choices and rights

  • Revoke access at any time. Visit myaccount.google.com/permissions and remove “Hermes Personal Backup”. Revocation stops all further access immediately; the operator can also simply delete the local token file.
  • Delete stored archives. The operator can delete any or all encrypted archives in the Drive folder at any time; deletion is immediate and permanent.
  • Request deletion or ask a question. Email aag262404@gmail.com. Because the only data subject is the operator, a request is normally fulfilled by deleting the Drive folder contents and revoking the grant.
  • Lawful basis (GDPR/UK GDPR framing). Processing is based on the consent given at the OAuth screen and on the legitimate interest of the data subject themselves (backing up their own data). Consent can be withdrawn without affecting prior lawful processing.

9. Security incidents

If the operator ever discovers that the token or an archive has leaked, the response is: revoke the OAuth grant, rotate the archive passphrase, delete the affected archives from Drive, and re-authorise. Notifications, where required, are handled between Google and the operator directly, since there are no other affected users.
